Module reference

Purpose, responsibilities, inputs, outputs, dependencies, and the reasoning behind each of the eleven modules — in dependency order.

·

config.py

Purpose
Single source of truth for paths, model name, and collection name.
Responsibilities
Resolve the project root; define the source PDF path, embedding model id, vector DB path, and collection name.
Inputs
None — derives everything from __file__'s location.
Outputs
PDF_PATH, EMBEDDING_MODEL, VECTOR_DB_PATH, COLLECTION_NAME.
Dependencies
pathlib only.
Design rationale
Centralizing config means every other module imports constants instead of hardcoding paths — one place to change if the project layout moves.
·

models.py

Purpose
Typed shapes that move through the pipeline.
Responsibilities
Define KnowledgeRecord, EmbeddedKnowledgeRecord, and SearchResult as dataclasses.
Inputs
None — pure data definitions.
Outputs
Three dataclass types imported everywhere else in the package.
Dependencies
dataclasses only.
Example
KnowledgeRecord(id="a1b2…", text="…", heading="Intro > Scope", page=3, source="brochure.pdf")
Design rationale
Dataclasses over dicts: field names are checked, IDE-discoverable, and every stage's contract is explicit rather than implied by string keys.
·

document_parser.py

Purpose
Turn a PDF on disk into a structured Docling document.
Responsibilities
Validate the file exists; run Docling's DocumentConverter.
Inputs
pdf_path: Path.
Outputs
A Docling DoclingDocument with headings, layout, and page provenance intact.
Dependencies
docling.document_converter.
Example
document = load_document(PDF_PATH)
Design rationale
Fails fast with FileNotFoundError before spending time spinning up a converter, so a missing PDF is diagnosed immediately, not buried in a Docling stack trace.
·

chunker.py

Purpose
Split a parsed document into semantically coherent chunks.
Responsibilities
Instantiate and run Docling's HierarchicalChunker.
Inputs
A Docling DoclingDocument.
Outputs
A list of Docling chunk objects, each carrying text, headings, and provenance.
Dependencies
docling.chunking.
Example
chunks = chunk_document(document)
Design rationale
Hierarchical (structure-aware) chunking over fixed-size windows — a chunk stops at a section boundary instead of mid-thought, which keeps retrieved context coherent.
·

chunk_mapper.py

Purpose
Convert Docling's chunk objects into the project's own KnowledgeRecord shape.
Responsibilities
Extract text, join heading breadcrumbs, read the first page number from provenance, read the source filename, and derive a deterministic id.
Inputs
A list of Docling chunks.
Outputs
A list of KnowledgeRecord objects.
Dependencies
hashlib, models.KnowledgeRecord.
Example
records = build_records(chunks)
Design rationale
The id is a SHA-256 hash of source|page|heading|text rather than a random UUID, so identical content always produces the identical id — the basis for idempotent ingestion downstream.
·

deduplicator.py

Purpose
Remove duplicate records before they reach embedding or storage.
Responsibilities
Collapse a list of records into a dict keyed by id, keeping one copy of each.
Inputs
list[KnowledgeRecord].
Outputs
list[KnowledgeRecord], deduplicated; also prints how many were removed.
Dependencies
models.KnowledgeRecord.
Example
records = deduplicate_records(records)
Design rationale
Runs before the expensive embedding step, so no compute is wasted embedding a chunk twice — and re-running ingestion on the same PDF is cheap and safe.
·

embeddings.py

Purpose
Turn text into vectors, for both ingestion and query time.
Responsibilities
Load BAAI/bge-base-en-v1.5 once; expose batch .embed() for records and single-string .embed_query() for questions.
Inputs
list[KnowledgeRecord] for .embed(); a str question for .embed_query().
Outputs
list[EmbeddedKnowledgeRecord]; or a single list[float] (768-d) for a query.
Dependencies
sentence_transformers, config.EMBEDDING_MODEL, models.
Example
embedded_records = embedding_service.embed(records)
query_vector = embedding_service.embed_query("What is Azure Data Factory?")
Design rationale
One model load, reused for every call, avoids the multi-second cost of reloading a transformer per request. Query embeddings are explicitly normalized for consistent cosine comparisons.
·

vector_store.py

Purpose
The only module that talks to ChromaDB.
Responsibilities
Open a persistent client and collection; upsert embedded records; run similarity search; reset or count the collection.
Inputs
list[EmbeddedKnowledgeRecord] for .store(); a query vector + top_k for .search().
Outputs
list[SearchResult] from .search(); an int from .count().
Dependencies
chromadb, config, models.
Example
vector_store.store(embedded_records)
results = vector_store.search(query_vector, top_k=5)
Design rationale
Isolating ChromaDB behind one class means the rest of the codebase never imports chromadb directly — swapping vector databases later touches this file only.
·

retrieval_service.py

Purpose
The public search API — the one thing other code (or MCP) should call to query the knowledge base.
Responsibilities
Embed the incoming question, then delegate to the vector store's search.
Inputs
question: str, top_k: int = 5.
Outputs
list[SearchResult].
Dependencies
embeddings.EmbeddingService, vector_store.VectorStore, models.
Example
results = retrieval_service.search("What is Azure Data Factory?", top_k=5)
Design rationale
Stateless by design — every call re-embeds and re-searches, so nothing about one query can leak into another, and the class is safe to share across concurrent MCP requests.
·

ingest.py

Purpose
Orchestrates the full offline ingestion run, end to end.
Responsibilities
Load → chunk → map → deduplicate → embed → store, in order.
Inputs
pdf_path: Path (defaults to config.PDF_PATH).
Outputs
A populated ChromaDB collection; console output describing what happened.
Dependencies
Every other Knowledge Base module.
Example
python -m Scripts.ingest
Design rationale
Kept as a single script rather than a class so it can double as both an entry point and a place to sanity-check the pipeline end to end while developing.
·

mcp_server.py

Purpose
Expose retrieval to any MCP client as a callable tool.
Responsibilities
Build one shared EmbeddingService / VectorStore / RetrievalService at import time; register and serve the search_knowledge_base tool via FastMCP.
Inputs
MCP tool call: question: str, top_k: int = 5.
Outputs
A list of plain dicts (via asdict()) — id, text, heading, page, source, distance per result.
Dependencies
mcp.server.fastmcp, Scripts.embeddings, Scripts.vector_store, Scripts.retrieval_service.
Example
python mcp_server.py   # starts the FastMCP server over stdio
Design rationale
Services are constructed once at module import, not per-request, so the embedding model stays loaded in memory across every tool call instead of reloading it each time.
